ODONTOGEST - HISTORIAS DE USUARIO
==================================

Roles del sistema:
  - Admin         → gestión de configuración, usuarios, reportes globales
  - Secretaria    → gestión operativa total (agenda, pacientes, finanzas, aprobación de turnos)
  - Paciente      → SIN cuenta. Guest checkout con DNI. Acceso solo por UUID.

──────────────────────────────────────────────────────
HU-001 | CENTRALIZACIÓN DE TURNOS                           ✅ COMPLETADA
──────────────────────────────────────────────────────
Como secretaria,
quiero asignar turnos buscando rápidamente al paciente por DNI,
para organizar la jornada de los doctores sin errores de duplicación.

Criterios de Aceptación:
  - El sistema permite buscar un paciente ingresando su DNI.
  - Si existe, los datos del paciente se autocompletan en el formulario.
  - El sistema valida que no existan turnos duplicados (mismo paciente,
    doctor, fecha y hora).
  - El turno queda asociado al doctor seleccionado.
  - Vista correspondiente: AgendaPage.tsx

HU-002 | CIERRE DE TURNO Y COBRO                            ✅ COMPLETADA
──────────────────────────────────────────────────────
Como secretaria,
quiero marcar un turno como realizado e ingresar el costo (ARS o USD)
apenas el paciente sale del consultorio,
para mantener la cuenta corriente actualizada al instante.

Criterios de Aceptación:
  - El turno puede marcarse como "Realizado" desde la vista de agenda.
  - Al marcarlo, se abre el Modal Multimoneda para ingresar el monto.
  - Se puede seleccionar divisa: ARS o USD.
  - Se puede registrar el método de pago: efectivo o transferencia/Mercado Pago.
  - El monto se registra en la cuenta corriente del paciente de inmediato.
  - Si no paga en el momento, queda registrado como deuda pendiente.
  - El modal permite elegir un servicio del catálogo (precarga precio editable)
    o ingresar "Servicio Manual" con descripción y precio libre.
  - Vista correspondiente: PagosPage.tsx, AgendaPage.tsx

HU-005 | REVISIÓN Y REFACTOR DEL BACKEND                    ✅ COMPLETADA
──────────────────────────────────────────────────────
Como desarrollador,
quiero que el backend siga buenas prácticas FastAPI,
para que el frontend React pueda consumirlo de forma segura y ordenada.

Criterios de Aceptación:
  - main.py usa routers separados por dominio (pacientes, turnos, finanzas, doctores).
  - crud separado por entidad con funciones tipadas.
  - models.py define relaciones explícitas con FK y backref.
  - schemas diferencia Request y Response por endpoint.
  - database.py expone get_db() para inyección de dependencias.
  - Todos los endpoints devuelven status codes HTTP correctos.
  - CORS habilitado para el frontend React.
  - Health check GET /health operativo.

HU-007 | AUTENTICACIÓN Y CONTROL DE ACCESO (INTERNO)       ✅ COMPLETADA
──────────────────────────────────────────────────────
Como administrador,
quiero que el sistema tenga login solo para el personal de la clínica,
para proteger los datos clínicos y financieros de accesos no autorizados.

Criterios de Aceptación:
  - Existen dos roles: admin y secretaria.
  - El paciente NO tiene cuenta. Accede al portal sin login (ver HU-008).
  - El sistema expone un endpoint POST /auth/login que devuelve JWT.
  - Las rutas del backend interno están protegidas: sin token válido → 401.
  - Las rutas del frontend están protegidas: sin sesión → redirige a /login.
  - La secretaria accede a agenda, pacientes, finanzas, catálogo y panel de aprobación.
  - El admin puede crear y gestionar usuarios desde un panel.
  - Los tokens tienen expiración y se renuevan automáticamente.
  - Las contraseñas se almacenan hasheadas (bcrypt), nunca en texto plano.
  - Rate limiting en endpoints públicos (slowapi).
  - Headers de seguridad HTTP (CSP, HSTS, X-Frame-Options, X-Content-Type-Options).
  - CHANGE correspondiente: CHANGE-009

HU-008 | PORTAL DE AUTOGESTIÓN (GUEST CHECKOUT)             🔲 PENDIENTE
──────────────────────────────────────────────────────
Como paciente,
quiero solicitar un turno desde mi celular sin tener que crear una cuenta,
usando solo mi número de DNI para identificarme,
y poder hacer seguimiento del estado de mi solicitud con un enlace único.

Criterios de Aceptación:
  - El portal es público: no requiere login ni contraseña.
  - Flujo en 4 pasos: Elegir Tratamiento → Elegir Doctor → Elegir Horario → Identificación.
  - Paso 1: cards del catálogo de tratamientos con nombre, precio, duración. Buscador + filtros.
  - Paso 2: selección entre doctores (Darío / Fabiana).
  - Paso 3: slots de 30 min como tarjetas, solo franjas mañana (9:00-12:30) y tarde (16:00-19:30).
    Sin jueves ni domingo.
  - Paso 4: ingresa DNI. El sistema verifica:
    - Si el DNI existe → muestra datos en modo lectura (nombre, apellido, celular, obra social).
    - Si el DNI no existe → formulario para cargar datos (shadow profile).
  - Al confirmar, el turno se crea con estado "solicitado" y recibe un UUID único.
  - El paciente recibe un enlace clickeable con el UUID para seguir su turno.
  - Si el paciente ya existía, se vincula el turno a su perfil. Si no, se crea automáticamente.
  - El email es opcional (personas mayores pueden no usarlo).
  - Página /consulta/:uuid muestra estado del turno y permite cancelarlo.
  - CHANGE correspondiente: CHANGE-007

HU-008b | PANEL DE APROBACIÓN (SECRETARIA)                  🔲 PENDIENTE
──────────────────────────────────────────────────────
Como secretaria,
quiero ver los turnos solicitados por los pacientes y poder aceptarlos o rechazarlos,
para mantener el control de la agenda y evitar superposiciones.

Criterios de Aceptación:
  - Panel "Solicitudes" en AgendaPage: lista de turnos en estado "solicitado".
  - Cada solicitud muestra: paciente, tratamiento, doctor, fecha/hora, obra social.
  - Aceptar: cambia estado a "pendiente" (confirmado en agenda) y notifica al paciente.
  - Rechazar: abre textarea para escribir motivo. Cambia estado a "rechazado".
    Notifica al paciente con el motivo para que elija otro horario.
  - La secretaria puede bloquear slots manualmente (tratamientos largos, pausas).
  - Slot bloqueado aparece gris oscuro en disponibilidad del portal.
  - La secretaria mantiene la potestad de crear pacientes y asignar turnos manualmente
    por teléfono/WhatsApp (flujo tradicional).

HU-009 | NOTIFICACIONES MULTICANAL + WHATSAPP BOT           🔲 PENDIENTE
──────────────────────────────────────────────────────
Como secretaria,
quiero que el sistema envíe notificaciones automáticas a los pacientes
por email y WhatsApp, incluyendo un bot conversacional,
para reducir los olvidos de turno y llamados manuales.

Criterios de Aceptación:
  - Al aceptar un turno, el paciente recibe notificación con link UUID.
    Prioridad: email (si tiene), WhatsApp (si tiene teléfono), sino solo UUID en pantalla.
  - Al rechazar un turno, el paciente recibe el motivo y puede solicitar otro horario.
  - Recordatorio 48h antes del turno.
  - Recordatorio 2h antes del turno.
  - WhatsApp Bot: el paciente escribe y el bot responde con opciones:
    "turno" → link al portal de autogestión.
    "secretaria" → deriva a la secretaria.
    "llamar" → número de teléfono de la clínica.
  - Los mensajes usan plantillas configurables.
  - El sistema no requiere acción manual para recordatorios.
  - CHANGE correspondiente: CHANGE-006
