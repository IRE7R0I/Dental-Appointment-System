ODONTOGEST - DESCRIPCIÓN DEL PROYECTO
======================================
Versión actual: v2.x (Backend operativo · Frontend React/TS operativo · PostgreSQL en producción)

OdontoGest es una plataforma de gestión clínica para centralizar la
administración de pacientes, turnos y finanzas en un consultorio odontológico.
El objetivo es descargar la carga administrativa de la secretaria, permitiendo
control del flujo de caja y la agenda médica en tiempo real.

ESTADO ACTUAL DEL PROYECTO
----------------------------
  Backend:         OPERATIVO (FastAPI + SQLAlchemy + Pydantic + PostgreSQL)
  Frontend:        OPERATIVO (React 18 + TypeScript + Vite + Tailwind CSS)
  Base de datos:   PostgreSQL (tablas creadas y operativas)
  Autenticación:   OPERATIVO (JWT + bcrypt + roles admin y secretaria)
  Health check:    OPERATIVO (GET /health en main.py)
  Seguridad:       OPERATIVO (JWT + rate limiting slowapi + security headers)

SEPARACIÓN FRONTEND / BACKEND (Arquitectura actual)
----------------------------------------------------
  Monorepo con dos proyectos bien separados:

  /backend     → Python + FastAPI    [operativo · refactorizado]
  /frontend    → React + TypeScript  [operativo · migración completada]

  La comunicación es exclusivamente por API REST (JSON).
  No hay lógica de negocio en el frontend, solo presentación y llamadas a la API.

ROLES DEL SISTEMA
------------------
  admin       → gestión de configuración (doctores, tratamientos, precios base),
                gestión de usuarios (crear, editar, activar/desactivar, eliminar
                secretarias), acceso a reportes financieros globales.
                Puede editar su propio usuario/contraseña (requiere contraseña actual).
  secretaria  → gestión operativa total: agenda, pacientes, finanzas,
                edición de tratamientos y precios, catálogo completo,
                aprobación de turnos, bloqueo de slots, creación de pacientes manual.
  paciente    → SIN CUENTA. Accede al portal vía guest checkout con DNI.
                Solo lectura y creación limitada: ver sus turnos por UUID,
                solicitar nuevo turno según disponibilidad. Sin login.

HORARIOS DE ATENCIÓN
---------------------
  Mañana: 09:00 a 12:30 (último turno 12:30)
  Tarde:  16:00 a 19:30 (último turno 19:30)
  Clínica cerrada: 13:00 a 16:00
  Sábado: solo mañana 09:00-12:30
  Sin atención: jueves y domingo
  Slots: cada 30 minutos (09:00, 09:30, 10:00, ...)

FUNCIONALIDADES IMPLEMENTADAS
------------------------------
  1. Gestión de pacientes: lista, perfil, edición, búsqueda y filtros.
  2. Agenda: turnos por doctor, vista por fecha, asignación con validación de duplicados.
  3. Historial clínico: por paciente, con tratamientos por turno, pagos y deuda.
  4. Página de historial dedicada: /pacientes/:dni/historial con layout de dos columnas.
  5. Finanzas y caja: cierre de turno con cobro multimoneda (ARS/USD), resumen diario.
  6. Cuentas corrientes: deudores, movimientos por paciente, saldo ARS y USD.
  7. Dashboard KPI: turnos del día, ingresos ARS y USD en tiempo real.
  8. Health check: GET /health devuelve estado del servidor y versión.
  9. Autenticación JWT: login para admin y secretaria con refresh automático.
  10. Panel de administración: gestión de usuarios (crear, editar, listar,
      activar/desactivar, eliminar secretarias). Solo admin.
  11. Catálogo de tratamientos y obras sociales: CRUD completo con precios ARS/USD,
      integración en modal de cierre de turno con precios editables.
  12. Gestión de doctores: CRUD completo con soft-delete y color de agenda por doctor.

DOCTORES
--------
  La clínica tiene dos doctores (Darío y Fabiana). Ambos gestionados desde el
  módulo de doctores con CRUD completo. El admin puede agregar/quitar doctores.
  La agenda los muestra por separado con vista filtrada y colores por doctor.

SEGURIDAD
----------
  - Autenticación JWT con bcrypt para usuarios internos (operativo)
  - Pacientes sin cuenta: acceso solo por UUID (no brute-forceable)
  - Rate limiting en endpoints públicos (slowapi, operativo)
  - HTTPS obligatorio en producción (Let's Encrypt)
  - Headers de seguridad: CSP, HSTS, X-Frame-Options, X-Content-Type-Options
  - CORS restrictivo en producción (solo dominio del frontend)
  - Contraseñas hasheadas, nunca en texto plano
  - Sin almacenamiento de datos de tarjetas de crédito
  - Backups diarios de la base de datos

NOTAS DE SEGURIDAD Y PRIVACIDAD
---------------------------------
  - El sistema maneja historias clínicas → cumplimiento Ley 25.326 (Habeas Data, Argentina)
  - Datos en tránsito protegidos por HTTPS (obligatorio en producción)
  - Backups diarios de la base de datos
  - Acceso por roles: los datos del paciente solo son accesibles por personal autorizado
  - Contraseñas hasheadas con bcrypt, nunca almacenadas en texto plano
  - Sin almacenamiento de datos de tarjetas de crédito
