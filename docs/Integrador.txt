4. ROLES DEL SISTEMA
────────────────────────────────────────────────
  admin       → gestión de configuración (doctores, tratamientos, precios base),
                gestión de usuarios, acceso a reportes financieros globales.
  secretaria  → gestión operativa total: agenda, pacientes, finanzas,
                edición de tratamientos y precios, aprobación de turnos,
                bloqueo de slots, creación de pacientes manual.
  paciente    → SIN CUENTA. Accede al portal vía guest checkout con DNI.
                Solo lectura y creación limitada: ver sus turnos por UUID,
                solicitar nuevo turno según disponibilidad. Sin login.

  Regla: el agente NUNCA debe exponer datos de otros pacientes al paciente anónimo.
  Regla: endpoints de reportes y finanzas solo accesibles por admin y secretaria.
  Regla: endpoints públicos (/portal/*, /consulta/*) protegidos solo por rate limit.

6. RESTRICCIONES TÉCNICAS ESTRICTAS
────────────────────────────────────────────────
  Backend:
    - Separar rutas por dominio usando APIRouter de FastAPI.
    - Usar inyección de dependencias con Depends(get_db) y Depends(get_current_user).
    - Schemas Pydantic separados: XxxCreate · XxxResponse · XxxUpdate.
    - CORS en producción restringido al dominio del frontend (no wildcard *).
    - Status codes HTTP correctos: 201 POST · 404 not found · 401 no auth · 403 forbidden.
    - Variables de entorno para SECRET_KEY, credenciales DB, API keys WhatsApp, SMTP.
    - NUNCA hardcodear secrets en el código fuente.
    - Rate limiting en todos los endpoints públicos (slowapi, 5-10 req/min por IP).
    - Headers de seguridad: CSP, HSTS, X-Frame-Options: DENY, X-Content-Type-Options: nosniff.
    - Nunca loguear DNI, email, teléfono ni historial clínico.

  Frontend (React + TS):
    - type Moneda = 'ARS' | 'USD'  →  NUNCA usar strings libres para moneda.
    - Toda llamada HTTP centralizada en /src/services/api.ts.
    - Interceptor en api.ts que adjunta Bearer token y maneja refresh automático en 401.
    - Sin lógica de negocio en componentes: solo presentación + hooks.
    - Tailwind para estilos, Material Design 3 como referencia visual.
    - Nunca mezclar CSS inline con clases Tailwind.
    - Rutas internas protegidas con <PrivateRoute>. Rutas públicas: /portal, /consulta/:uuid.
    - El portal usa stepper (4 pasos), sin recargar la página entre pasos.

  Seguridad:
    - Contraseñas hasheadas con bcrypt (passlib). Nunca en texto plano.
    - JWT con expiración: access token 30 min, refresh token 7 días.
    - Pacientes sin cuenta: acceso a turnos solo por UUID v4 (2^122 combinaciones).
    - Datos clínicos nunca expuestos en logs ni mensajes de error.
    - GET /pacientes/verificar/{dni} solo devuelve datos no sensibles (sin email, sin historial).

  General:
    - No duplicar lógica entre frontend y backend.
    - No hardcodear URLs: usar variables de entorno (.env).
    - Separación estricta: /backend y /frontend como proyectos independientes.

    GET    /pacientes                → listar pacientes
    GET    /pacientes/deudores       → listar pacientes con saldo > 0
    GET    /pacientes/historial?dni=X&fecha_desde=&fecha_hasta= → historial con turnos, tratamientos y pagos
    GET    /pacientes/verificar/{dni} → (CHANGE-007 — pendiente) público, verifica si DNI existe

    PUT    /pacientes/{dni}          → actualizar paciente
    GET    /pacientes/{dni}/cuenta   → detalle de movimientos de cuenta corriente

  /turnos                            (✅ operativo, ampliar en CHANGE-007)
    GET    /turnos?fecha=&id_doctor=&paciente_dni= → listar (filtros opcionales)
    GET    /turnos/hoy               → turnos del día actual
    GET    /turnos/solicitados       → (CHANGE-007 — pendiente) turnos en estado solicitado
    GET    /turnos/paciente/{dni}    → turnos de un paciente específico
    POST   /turnos                   → crear turno
    POST   /turnos/bloquear          → (CHANGE-007 — pendiente) bloquear slot manualmente
    PUT    /turnos/{turno_id}/cerrar → cerrar turno con cobro

    PUT    /turnos/{id}/rechazar     → (CHANGE-007 — pendiente) rechazar con motivo

9. ESTADOS DEL TURNO
────────────────────────────────────────────────
  solicitado    → paciente envió solicitud desde el portal, espera aprobación
  pendiente     → secretaria aceptó la solicitud (confirmado en agenda)
  confirmado    → sinónimo de pendiente, por compatibilidad
  bloqueado     → secretaria bloqueó el slot manualmente (sin paciente)
  realizado     → atendido y cobrado (cierre de turno)
  cancelado     → cancelado por paciente o secretaria
  rechazado     → secretaria rechazó la solicitud (incluye motivo en motivo_rechazo)

  Transiciones válidas:
    solicitado    → pendiente   (secretaria acepta)
    solicitado    → rechazado   (secretaria rechaza, con motivo)
    solicitado    → cancelado   (paciente cancela vía UUID)
    pendiente     → realizado   (secretaria cierra con cobro)
    pendiente     → cancelado   (secretaria o paciente vía UUID)
    bloqueado     → cancelado   (secretaria libera)

  Nota: Actualmente models.py usa valores simplificados ("Pendiente", "Asistió",
  "Canceló"). CHANGE-007 migrará a los estados completos definidos arriba.
